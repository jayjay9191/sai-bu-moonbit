# 赛簿 · MoonBit 版

一本管所有比赛的账。

> 曾用名：参赛管家（2026-11-16 改名）。

一个帮参赛者**同时管多个比赛**的命令行工具：19 个比赛的规则、截止、材料放进一个台账，
一件作品投不同比赛时自动检测规则冲突、生成投稿包。

参加 **2026 MoonBit 黑客松 11 月赛季**的作品。原创 MoonBit 实现，
没有复制任何其他项目的代码。

## 这是什么

对标 Lexmount 一等奖作品 Auto-Lexmount（一键全自动参赛流水线），但比它多三样东西：

1. **多比赛并行管理**——Auto-Lexmount 一次只做一个比赛；这里 19 个比赛的规则、
   截止、材料、奖金放在一个台账里统一管理（12 个在途 + 7 个关注）。
2. **游戏作品投稿支持**——Auto-Lexmount 只会读 1–3 个公开网页做小报告，
   做不了游戏；这里能打包游戏链接、演示视频、投稿文案。
3. **冲突检测**——同一件作品投不同比赛，规则撞了就报警。核心卖点：
   魔搭要求“活动期间首次公开发布”，《第零次黎明》11-02 前已公开且已投
   Qoder / AI PLAY，工具直接报 P0，而不是悄悄交上去等取消资格。

## 采用（自用）

本工具正在管理 AI 工具定价核验的参赛：该作品已登记为台账里的
第 4 件作品（1000 条 AI 工具官网定价 + 5 步证据链 + 14 项验证规则，
2026-11-16 首次公开，未投过任何比赛），冲突检测与投稿包生成均已
覆盖——2026-11-16 实测 3 个冲突：魔搭 P0（首次发布）、知乎 S3 P1
（须新做）、造化 P1（须新做）；软件创新大赛无冲突（原创条款只看
是否投过其他比赛）。

诚实标注：这是作者自用——赛簿与定价核验是同一作者的两个
MoonBit 参赛作品，目前没有外部用户。定价核验的 MoonBit 报名表
尚未填。

## 怎么跑

需要 MoonBit 工具链（`moon`，0.1.20261104 或更新）。

```sh
# 1. 跑测试（219 个：MoonBit 183 个 + Python 36 个，全部通过才算数）
moon test
python3 -m unittest discover -s tests_py

# 2. 跑 CLI：无参数跑整条流水线
#    打印 19 个比赛台账 → 冲突检测 → 截止撞期提醒 → 投稿包
moon run cmd/main

# 3. 子命令：只做一件事（作品名、比赛名含空格时加引号）
moon run cmd/main list
moon run cmd/main conflicts 第零次黎明
moon run cmd/main pack 第零次黎明 "松江·创世纪 AI 游戏大赛"
moon run cmd/main collisions
moon run cmd/main benchmark
moon run cmd/main validate
moon run cmd/main preflight
moon run cmd/main help
```

不需要联网、不需要 API Key、不读写任何外部服务，纯本地运行。
只有 `scripts/sync_data.py` 需要联网（抓五个公开官网核对数据）。

### 提交前检查（pre-commit 钩子）

```sh
bash scripts/setup-hooks.sh   # 只需跑一次：把本地仓库的钩子指向 .githooks
```

此后每次 `git commit` 都会先跑 `moon test`，失败则阻止提交。
钩子放在 `.githooks/pre-commit` 里随仓库走——git 默认不提交
`.git/hooks` 下的钩子，所以不能直接放那里；`core.hooksPath` 是
本地仓库配置，不进 git，换电脑或重克隆后要重跑一次启用脚本。
钩子只跑 `moon test`（保持提交前检查够快）；完整检查是上面
的三条（`moon test` + Python 测试 + preflight）。

## 数据怎么改（JSON 是唯一数据源）

比赛数据不在 `.mbt` 代码里，全部在 `data/competitions.json`：

```sh
# 1. 改 JSON（只改这个文件）
# 2. 重新生成数据代码
python3 scripts/generate_data.py
# 3. 格式化 + 校验 + 测试（生成器输出必须先过 moon fmt 再提交）
moon fmt && moon run cmd/main -- validate && moon test
```

生成器是确定性的：同一份 JSON 每次生成字节一致；生成内容已验证
与外置前的 `competition.mbt` 数据逐字一致（135 个字符串 + 36 个布尔值）。
CI 里也有一道检查：改 JSON 却忘了重新生成，流水线会失败。

## 同步：联网核对官方信息

```sh
python3 scripts/sync_data.py            # 核实并更新（有变化才写 JSON）
python3 scripts/sync_data.py --dry-run  # 只打印报告，不改任何文件
```

覆盖 5 个公开可读的来源：MoonBit 官网（11 月轮截止是否公布，只报告）、
绿联官网（初稿截止与总奖金池）、PAYATHON 官网（两阶段最后一天与
Vibe Pay 一等奖）、松江专题页（投稿截止，只核实）、涌现奖官网
（提交截止，只核实）。其余 14 个比赛因页面打不开、登录墙、或日期不在
公开页上，脚本不碰，只在报告里列出。明确标注的值可以自动更新；
需要推断的值（PAYATHON 日历格的阶段最后一天）只核实不自动写，
对不上就报“需人工确认”。

## 60% 借鉴 / 40% 创新（诚实说明）

**借鉴 60%（学的是思路和工程做法，不是代码）：**

- 证据优先：每条比赛数据带来源与核实状态，没核到的直接标“未核实”/“待核对”，
  不编数据。数据来源是《最近要参加的比赛汇总》（2026-11-13 晚四路核实版）。
- 严格的提交前检查：投稿包生成前先跑冲突检测，P0 冲突直接把投稿包标为 blocked，
  而不是生成一份看起来能交的材料。
- 预检清单与清单哈希：提交前逐项检查（演示产物拒绝、清单哈希重算、
  测试必须通过、真实证据、截止未过期）、产物带 SHA-256、结果未知
  不自动重试（学 Auto-Lexmount 的 submission.py / workflow.py /
  release.py；2026-11-15 晚全量重读过它的代码，见设计手记 §6；
  代码一律没抄——仓库无 LICENSE，且语言不同）。
- 诚实标注：演示/转述/未核实的东西在数据和输出里写清楚
  （例如魔搭“首次发布”条款注明来自 AIBetas 转述，官网原文未直接读到）。
- 测试覆盖：核心逻辑（台账、冲突、投稿包）都有测试，`moon test` 全过才算完成。

**创新优化 40%（Auto-Lexmount 没有的）：**

- 多比赛并行管理（19 个比赛一个台账，按截止排序；12 个在途 + 7 个关注）。
- 游戏作品投稿支持（打包游戏链接 + 演示视频 + 投稿文案）。
- 跨比赛冲突检测（首次发布 / 须新做 / 未参加过其他比赛 / 截止撞期）。

### 同步覆盖 5 → 19：分三批

红线先立好：沿用 §2 的教训——只有页面上**明确标注**的值才自动更新，
需要**推断**的值只核实、不自动写，对不上就报“需人工确认”。
“覆盖 19 个”指的是脚本里对 19 个比赛都有检查，不是 19 个都能自动更新：
登录墙、打不开的页面永远只能报告，不能硬写数据。

- **第一批（先试能读的）：**新增 7 个“关注”里还没试过同步的 6 个——
  十方融海、DoBe、中小企业、CAAI 青年赛、兴智杯（造化已于 2026-11-14
  人工核实，先试它有没有公开可读的页面），加上前 8 个里可能有公开页
  的。做法照松江 / 涌现奖的成功经验：先找专题页明文，再找 JS 包搜文本。
  每加一个来源，先 `--dry-run` 看报告，确认 0 项误更新再合入。
- **第二批（只报告、不硬写）：**确认打不开或登录墙的——Qoder、魔搭、
  AI PLAY、BayHack、荣耀、华为、知乎 S3、Rokid。脚本只报告“页面状态”
  （打不开 / 登录墙 / 日期不在公开页上），数据仍靠人工核对更新 JSON。
  这批的目标是“状态可查”，不是“数据自动更新”。
- **第三批（接 verified_at）：**同步脚本核实通过时，自动更新该行的
  `verified_at`——现在它靠人工维护（见设计手记 §4），核实了也不自动写。
  规则（2026-11-16 定，接之前先立好）：
  1. 只更新脚本实际查过的字段对应的行：某行只有在其检查覆盖的
     全部字段都被确认（页面值与台账一致，或页面明确标注的值被自动
     更新）时，才把 `verified_at` 更新为运行当天日期（用户时区
     Asia/Shanghai；VM 是 UTC，直接取 `date.today()` 会差一天）。
  2. 任一覆盖字段未核实（抓取失败、页面无该字段、推断值对不上报
     “需人工确认”）→ 该行 `verified_at` 不动。
  3. 推断值只核实、不自动写（PAYATHON 日历格）：推断值对上才算确认，
     对不上整行不更新。
  4. 只报告的检查（MoonBit、第二批 8 个）永远不更新 `verified_at`：
     它们的合同是“状态可查”，不是核实字段——荣耀参赛协议页、知乎
     活动列表页即使在报告里对上了日期，也不写 `verified_at`，
     仍靠人工核对后手动更新。
  5. `dry-run` 只报告“哪些行会被更新”，不写 JSON。
  6. `verified_at` 是数据镜像：生成测试的 `ROW_EXPECT` 里
     `verified_at` 一列跟随同步核实结果走（只改日期值）；冲突等级
     与标志位期望仍以人工底稿为准，改它们先改底稿。
  （2026-11-16 已接：绿联、PAYATHON、松江、涌现奖、CAAI 青年赛
  5 行核实通过，`verified_at` 更新为 2026-11-16；其余行不动。）

### 运行时 JSON 加载（Plan A）：取舍说明

- **优点：**改 JSON 不用重编译，用户可以直接改数据文件；工具更像一个
  “带数据的工具”，而不是“写死数据的程序”。
- **代价：**main 要改异步（core 只有 `async/fs`，没有同步读文件 API）；
  启动时要找 `data/competitions.json` 的路径（从哪个目录启动，结果就
  不一样）；部署要多带一个数据文件；CI 要多一道“数据文件在不在”的检查；
  加载失败、缺字段时的报错处理都要另写代码。取舍细节见设计手记 §8.2。
- **结论：**先不做。现在台账 19 行、靠人工更新，JSON + 生成器够用。
  触发条件写清楚再动手：比赛数翻倍（到 40 行左右），或者每周要改多次
  数据——到那时再评估 Plan A，生成器方案作为对照组保留。
