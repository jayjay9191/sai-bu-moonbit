# 设计与实现手记（2026-11-15）

仿照《坦克儿大冒险》作者手记的写法：只写真实做过的决策，
每个决策带数字和代价，不讲空话。下面三件事都是本项目实际发生过的。

## 1. 数据外置：JSON + 生成器，而不是运行时读文件

**决策：**`data/competitions.json` 是唯一数据源，
`scripts/generate_data.py` 从它生成 `competition_data.mbt`；
运行时不读任何外部文件。

**为什么不用运行时读 JSON（方案 A）：**MoonBit core 没有同步读文件
的 API，只有 `moonbitlang/core/async/fs`。异步 main 加上工作目录
路径问题，拼起来太脆弱。方案 A 在写代码前就放弃了，没有为它
写过一行实现。

**方案 B（实际做的）长什么样：**

- `data/competitions.json`：19 个比赛（12 个在途 + 7 个关注）+ 3 件作品。
  （2026-11-15 第 5 轮从 12 个扩到 19 个；本节其余内容不变。）
- `scripts/generate_data.py`：确定性输出，同一份 JSON 每次生成
  字节一致（字段按固定顺序输出）。
- 核对过：生成内容与外置前的内联数据逐字一致（135 个字符串 +
  36 个布尔值）。
- CI 里有一道检查：改 JSON 却忘了重新生成，流水线失败
  （`git diff --exit-code -- competition_data.mbt`）。

**代价（承认）：**改数据要多跑一步生成（`python3
scripts/generate_data.py` + `moon fmt`），运行时数据改不了，
不重新编译就不能变。台账只有 19 个比赛、靠人工更新，这个代价
可以接受；如果工具要跟踪实时变化的规则，这个方案就不够。

## 2. 同步脚本的真实 bug：把报名开始日当成了截止日

**发生了什么（2026-11-15，开发中）：**第一版 `scripts/sync_data.py`
取 PAYATHON 截止日的方法，是拿日历里第一个包含“报名”的格子——
那个格子是 **2026-09-21，报名开始日**，不是截止日。脚本把它写进
JSON，台账被改坏了。

**怎么发现的：**跑完后 JSON 的 diff 显示截止日变成了一个比比赛
开始还早的日期；对照官网原文确认是错的。

**修复（两部分）：**

1. 用 git 把 JSON 恢复原样（`git checkout`），没有手动去改
   那个被写坏的值。
2. 永久改了更新策略：
   - 只有页面上**明确标注**的值才自动更新：绿联初稿日期与总奖金池
     （页面上“初稿作品提交”带 `datetime` 属性、“总奖金池 ¥34,000”），
     PAYATHON Vibe Pay 一等奖（页面明文“Vibe Pay，一等奖，数量 1，
     税前 ¥30,000”）。
   - 需要**推断**的值只核实、不自动写：PAYATHON 日历格里某阶段的
     最后一天（阶段内日期取最大值）。对不上台账就报“需人工确认”，
     JSON 一动不动。
   - 删掉了之前那个宽松的 MoonBit 日期正则（它能匹配页面上任意
     像日期的字符串）；MoonBit 检查现在只报告页面是否还写
     “以官方通知为准”。

**最后一次实测（2026-11-15，作者亲自重跑）：6 项检查，0 项更新，
JSON 未改动**——绿联初稿 2026-12-07 ✓ + 奖金池 ¥34,000 ✓；
PAYATHON 报名最后一天 2026-12-01 ✓、作品提交最后一天 2026-12-09 ✓、
Vibe Pay 一等奖 ¥30,000 ✓；MoonBit 11 月轮截止仍写
“以官方通知为准”，未公布。

**教训：**会写数据的同步脚本就是个风险点，除非每一次写都绑在
页面明确标注的值上。推断只配进报告，不配进数据。

## 3. Benchmark 与人工基线：怎么测的、数字是多少

**Benchmark（`moon run cmd/main benchmark`）：**

- 测法：先跑一轮全量扫描数真实结果（全部 3 件作品 × 全部 19 个比赛
  的冲突检测与投稿包生成），再把同样的全量扫描重复 100 轮计时。
- 一轮 = 171 次规则评估（3 件作品 × 19 个比赛 × 3 条规则：
  首次发布 / 须新做 / 未参加过其他比赛）。
- 2026-11-15 在本机当场跑出来的数字：**100 轮总计 4–8 毫秒，
  平均每轮约 40–80 微秒**。多次跑在 4–8 毫秒之间——量级在几毫秒，
  不要把某个具体毫秒数当精确值较真。
- 全量扫描的结果：冲突 8 个（P0 6 个，P1 2 个），投稿包 57 个
  （其中 P0 挡住 6 个），截止撞期 3 个日期（11-30、12-01、12-06）。
- 上一轮（12 个比赛、2 条规则）的数字：100 轮 7 毫秒（三次跑 7、8、7），
  冲突 4 个（P0 3、P1 1），投稿包 36 个（挡住 3 个），撞期 2 个日期。
  规则从 2 条变 3 条、比赛从 12 个变 19 个，耗时仍在几毫秒量级。

**人工基线（2026-11-15，逐格底稿见
`docs/manual-baseline-2026-11-15.md`）：**

- 测法：对照已整理好的台账，逐项手查全部 57 格（3 件作品 ×
  19 个比赛），按 `conflict.mbt` 的三条规则逐格判断。
- 耗时：**本轮未单独计时**（57 格是边做边逐格核对的，不编一个秒数）。
  上一轮 36 格约 7 秒，只覆盖“对照台账逐格判断”这一步。
- 结果：与工具完全一致——冲突 8 个（P0 6 个，P1 2 个），
  投稿包 57 个（其中 P0 挡住 6 个），撞期 3 个日期。

**诚实限定（引用这两个数字前请先读）：**

1. 人工核对**不是盲测**：核对前已经看过工具的结果，所以这次的
   “0 漏检”不能当强证据。
2. 7 秒是 AI 速度的下限，只覆盖“对照已整理好的台账逐格判断”
   这一步，不含整理台账本身的时间（查 19 个比赛的规则页、核实
   每条规则）。真人对照 19 个比赛的原始规则页逐项核对，耗时只会
   更久，具体多久没测过，不编数字。

## 4. 台账每行最后核验时间（verified_at）

**做了什么：**`Competition` 结构加 `verified_at` 字段（YYYY-MM-DD），
表示该行截止与奖金最后一次对照官方来源核实的日期；`validate`
校验它的格式；19 行全部有效；坏日期（`2026-13-01`）检出 1 个问题。

**日期的依据：**

- 10 行是 **2026-11-13**：那晚完成了 12 个比赛的全量核实轮次
  （四路核实版汇总），是每行最后一次全面核对的日期。
- 9 行是 **2026-11-15**：绿联、PAYATHON（当天同步脚本重跑实测
  8 项检查、0 项更新，核实了这两行的截止与奖金）+ 新增的 7 个
  “关注”比赛（造化是 2026-11-14 核实的，其余 6 个是 2026-11-15
  核实的；兴智杯的截止未核实，见下）。

**诚实限定：**`verified_at` 只表示“截止与奖金这两个字段最后一次
对照官方来源核实”的日期。绿联和 PAYATHON 的 2026-11-15 只覆盖
同步脚本能查的字段（绿联初稿日期与奖金池、PAYATHON 两阶段最后一天
与一等奖），那两行的其他内容（赛道要求、材料清单）仍是 2026-11-13
的基线。写 2026-11-15 不等于整行都重核过。另外 `verified_at`
目前靠人工维护，同步脚本核实通过时不会自动更新它。

## 6. 读 Auto-Lexmount 全量代码之后：学了什么、改成什么、什么是新增的

**读了什么（2026-11-15 晚）：**TorinTao 的 Auto-Lexmount 公开仓库
（https://github.com/TorinTao/auto-lexmount，2026 Lexmount 揽岳
挑战赛一等奖作品），克隆到 /tmp 临时目录读完即弃，没进本仓库。
读时 HEAD 是 b754736 之后的 2 个新提交，比早上分析时又长了。
核心 `autolex/` 约 2,947 行（workflow.py 461、server.py 335、
release.py 197、quality.py 188、reader.py 166、clients.py 150、
visual.py 152、cli.py 138、submission.py 139、runner.py 117、
citations.py 70、config.py 57、common.py 52、demo.py 42、design.py 77、
presentation.py 72、release_browser.py 171、reader_presentation.py 36），
30+ 辅助脚本；测试 Python 152 项（grep 计数）+ 前端 17 项 = 169 项
（它 README 自称的 123+17 是 batch7 时的旧数）。

**红线（写在前面）：**那个仓库**没有 LICENSE 文件**，代码一律没抄、
没复制粘贴、没以它的代码为底子改。语言本来也不同（它是 Python，
这里是 MoonBit），抄也抄不过来。下面每条都写清“它的做法 →
改成了什么”，改动的部分是自己重写的。

**学到的设计（9 条）：**

1. **分阶段流水线 + 每阶段产物带 SHA-256 + 断点续跑**（workflow.py）：
   STAGES = rules→ideas→build→test→package；state.json 记录已完成
   阶段 + 每个产物的 SHA-256；续跑跳过已完成阶段；保存的产物被改过
   就拒绝（"Saved artifact changed or missing…; use a new run directory"）；
   brief/revision 开始后不可变；fcntl 锁防并发。
   → 改成：`preflight` 是单次全链路（validate → 行核验 → 冲突 →
   投稿包认证 → 撞期），不做断点续跑——本地 CLI 单次运行几毫秒，
   没必要；清单哈希 = 全部台账数据的规范序列化再算 SHA-256
   （对应它的 state.json 产物哈希）；数据自相矛盾整单拒绝
   （对应“产物被改过就拒绝”）；不做锁——单用户本地工具，无并发场景。
2. **预检清单**（submission.py）：只有完成的 LIVE 运行能提交，
   演示运行拒绝；manifest.json 哈希必须与 state.json 记录一致；
   每个打包文件重算哈希比对；测试必须通过；真实证据；截止必须
   存在且在未来；视觉验收绑定最终页面哈希；真实作者 +
   artifact_links；表单映射须检查成功选择器。
   → 改成：`certify_pack` 的三条认证条件（无 P0、材料无缺口、
   该行已核实且未过期）+ `row_verdict` 的三项判断（已过截止 /
   未核实标记 / 核验过期 30 天）+ validate 失败整单拒绝。
   没照搬的：没有 LIVE/DEMO 运行之分（本工具不联网、不真的提交，
   没有“运行”可分）；没有视觉验收（CLI 无页面）；没有表单映射
   （不填任何表单）。
3. **SHA-256 处处**（input_sha256、code_sha256、source_manifest_sha256、
   archive_sha256、identity hash、manifest.json = {filename: sha256}）。
   → 改成：纯 MoonBit 自己写的 SHA-256（FIPS 180-4，core 没有
   crypto 包）；清单哈希 = 规范序列化后的 SHA-256；8 个向量用
   Python hashlib 对过；清单哈希与 Python hashlib 在真实台账上
   逐字一致。没照搬的：只对清单整体算一个哈希，不对每个产物逐个算——
   本工具的“产物”就是台账数据本身。
4. **结果未知不自动重试**（submission.py + release.py）：提交超时标
   unknown、“automatic retry disabled”、必须人工去官网核对；恢复
   只针对不确定的*发布*，且须独立验证的 URL。
   → 改成：preflight 是纯本地单次运行，根本没有重试逻辑；失败原因
   逐项打印；退出码只在 validate 失败时为 1，单个包的拒绝是结论，
   不是进程失败。没照搬的：没有发布/提交动作，所以没有 unknown 状态。
5. **证据优先验证**（workflow.validate_rules、runner.validate_output、
   quality.robustness）：引用必须逐字出现在源证据里；评审结论必须
   与检查结果一致；数量与 brief 核对；鲁棒性扰动测试，崩溃不算
   有效拒绝。
   → 改成：verified_at 每行 + 未核实标记扫描 + validate 校验；
   引用校验在 web v1 里有，MoonBit 版用 verified_at + preflight
   行核验承接。没照搬的：没有模型调用，所以没有“引用逐字核对”和
   鲁棒性扰动测试——本工具的输入是人工核实过的台账，不是模型输出。
6. **演示与真实区分标注**（workflow.package、demo.py）：报告横幅
   "DEMO — 离线固定样例，不能作为参赛云端证据" vs "LIVE"；
   README 明说 demo 不是云端实践证据、不能投稿。
   → 改成：preflight 的认证结论本身就是这个标注——“可提交”与
   “不可提交（原因）”；README 的“哪些是真实数据，哪些是演示”
   一节；造化规则 2 的诚实限定。没照搬的：没有 DEMO/LIVE 两套
   运行模式（本工具没有云端运行）。
7. **README 诚实写法**（验证日志带日期与精确数字、收据编号、
   明确的局限）。
   → 改成：README 的实测数据表（带分母）、验证记录表、
   范围与未完成事项、设计手记本文件；测试数 179 项带分母；
   benchmark 表带人工基线对照与三个诚实限定。
8. **错误处理卫生**（common.py redact：存下来的错误是受控信息，
   不存原始 SDK 异常防泄密；CLI 只打印通用类型名）。
   → 改成：本工具不调任何 SDK、无密钥，错误信息全部是受控的
   中文文案（validate 问题列表、preflight 拒绝原因）；没有需要
   脱敏的东西。
9. **测试结构**（unittest 按模块分 class、InTemp 临时目录、demo 夹具
   集成测试、前端 DOM 替身测试）。
   → 改成：MoonBit 黑盒测试按文件分（主测试 52 + 生成测试 79 +
   preflight 测试 26）+ Python unittest 22；生成测试由生成器从
   人工基线底稿产出（生成器只校验名字存在，不读期望值）；回归测试
   覆盖已知的两个 bug（P0 空括号、PAYATHON 日期）。

**没拿的东西：**浏览器自动化、Docker、模型调用、服务器、视觉验收、
表单提交、锁文件、断点续跑——本工具是本地离线 CLI，不需要这些。

**自己的新增优化（Auto-Lexmount 没有的）：**

- 19 比赛台账（12 个在途 + 7 个关注，plan_status 字段）。
- 规则 3（原创条款 P0）+ 规则引擎数据驱动（3 条规则/格）。
- verified_at 每行 + 30 天过期政策（STALE_DAYS，写在代码里不藏着）。
- sync 脚本（5 个来源，只核实不自动写；推断值只进报告）。
- 57 格逐格断言生成测试（期望值来自人工基线底稿，不来自 JSON）。
- 纯 MoonBit SHA-256 + Hinnant 日期换算（core 缺这两个能力，自己写）。
- preflight 逐包认证（可提交 / P0 挡住 / 材料缺口 / 数据未核实，
  拒绝原因逐项）。

## 8. 架构对比：两个关键取舍（2026-11-16）

仿照坦克儿手记的做法：把“为什么选这个、放弃了什么”写下来，
免得以后自己忘了当初为什么没走另一条路。两个取舍都是真实发生过的，
没走的那条路没有为它写过一行实现。

### 8.1 preflight 的 SHA-256：纯 MoonBit 实现 vs 调外部命令

**选了纯 MoonBit 实现**（`sha256.mbt`，123 行，FIPS 180-4）：

- MoonBit core 没有 crypto 包（grep 过，无 sha256），没有现成可调的库，
  想用标准库这条路根本不存在。
- 工具承诺“纯本地运行，不读写任何外部服务”——调 `sha256sum` /
  `shasum` 是调外部命令，平台还不统一（Linux 有 `sha256sum`，
  macOS 默认是 `shasum -a 256`，Windows 默认没有），CI
  （ubuntu-latest）和作者本机（Windows）会走两套行为，
  清单哈希“同一份数据同一个值”的承诺就站不住。
- 代码里现在没有任何外部命令调用（grep 验证过），“零外部调用”
  本身就是可验证的卖点；preflight 的清单哈希在 CI 和本机算出来
  是同一个值（`7652425c…caa5`），不需要解释环境差异。

**放弃了什么：**

- 性能：纯实现比系统工具慢。但清单只有 19 行台账数据，单次哈希
  的量很小，性能不是决定因素——全量扫描 100 轮才 7–8 毫秒，
  哈希不在瓶颈上。真到数据量大到哈希成为瓶颈那天，再考虑换方案。
- 维护成本：123 行标准算法自己扛，出错没人兜底。兜底办法是 8 个
  用 Python hashlib 对过的测试向量 + 真实台账的清单哈希与 Python
  hashlib 逐字一致。
- “用系统工具更可信”的默认信任：系统工具是经过千锤百炼的，
  自己写的不是。这份不信任要靠向量测试和逐字一致来还，
  不是靠口号。

### 8.2 数据：JSON + 生成器 vs 运行时加载

**选了 JSON + 生成器**（决策本身见 §1，这里补取舍）：

- 为什么：core 没有同步读文件 API，只有 `async/fs`；异步 main
  加上工作目录路径问题，拼起来太脆弱；生成器确定性输出，
  CI 能检查“改 JSON 忘生成就失败”，数据改动进 git diff 可审。
- 放弃了什么：改数据必须重新生成 + 重新编译，运行时改不了；
  用户拿到二进制改不了台账，必须走源码；数据编译进二进制，
  数据与程序绑死。

**没走的那条路（运行时 JSON 加载，Plan A）的取舍：**

- 优点：改 JSON 不用重编译，用户可以直接改数据文件，工具更像
  一个“带数据的工具”而不是“写死数据的程序”。
- 代价：main 要改异步；启动时要找 `data/competitions.json` 的路径
  （从哪个目录启动，结果就不一样）；部署要多带一个数据文件；
  CI 要多一道“数据文件在不在”的检查；加载失败、缺字段时的
  报错处理都要另写代码。
- 结论：现在台账 19 行、靠人工更新，生成器够用，Plan A 先不做，
  留到 README“下一步路线图”里，等台账规模或更新频率上去再评估。

## 9. verified_at 自动更新（2026-11-16，同步覆盖三批的第三批）

**规则（先写进 README“下一步路线图”第三批，再接线）：**
只更新脚本实际查过的字段对应的行——某行检查覆盖的全部字段都被
确认（页面值与台账一致，或页面明确标注的值被自动更新），才把该行
`verified_at` 更新为运行当天日期；任一字段未核实，该行不动；推断值
（PAYATHON 日历格）对上才算确认，对不上整行不更新；只报告的检查
（MoonBit、第二批 8 个）永远不更新 `verified_at`；dry-run 只报告
“哪些行会被更新”，不写 JSON。

**一个时区坑（实测抓到的）：**VM 是 UTC，直接用 `date.today()` 会差
一天——UTC 11-15 17:00 就是 CST 11-16 01:00。第一次 dry-run 只算出
2 行要更新（绿联/PAYATHON/CAAI 已是 11-15，按 UTC 日期算“不用改”），
当场发现不对，改成 `today_cst()`（UTC+8，中国无夏令时），dry-run
才算出正确的 5 行。`verified_at` 必须按用户日期写。

**首次运行（2026-11-16）：**核实通过 5 行，`verified_at` 全部更新为
2026-11-16——绿联、PAYATHON、松江、涌现奖、CAAI 青年赛；0 项其他
更新；JSON diff 逐字段核对过：只动了这 5 行的 `verified_at`，works
数组一字未动。生成测试的 `ROW_EXPECT` 里 `verified_at` 一列是数据
镜像，跟随改了 5 个日期值（只改日期，不改冲突/标志位期望），
重新生成后测试全过。

**有意没做的：**荣耀参赛协议页、知乎活动列表页在报告里对上了日期，
但它们是第二批“只报告”的检查，按规则不更新 `verified_at`，仍靠
人工核对后手动更新——报告-only 检查的合同是“状态可查”，不是核实
字段；想让它们也自动更新，先把它们升格为核实检查，再改规则。
