# 引用校验与投稿包认证：完整案例

本文是赛簿“引用校验追踪”的完整演示：一次规则判定如何从
“规则适用条件 → 来源证据 → 结论”走完，每一步都能指着来源说话。

背景：2026-11-18 报名初审驳回指出，申报书承诺的引用校验与投稿包认证，
缺少从规则适用条件、来源证据到结论的清晰机制和代表性案例。
本文就是那个机制的代表性案例，全部用真实台账数据。
机制实现在 `evidence.mbt`，复现命令：

```sh
moon run cmd/main trace 第零次黎明 "魔搭 AI+∞ 第三期「AI 造游戏」"
moon run cmd/main trace 验价尺 "第二十届全国大学生软件创新大赛"
moon run cmd/main trace 第零次黎明 "松江·创世纪 AI 游戏大赛"
moon run cmd/main trace 第零次黎明 "知乎黑客松 S3"
moon run cmd/main trace 第零次黎明 "TapTap 游戏上架"
```

## 机制：三步链

1. 规则适用条件：每条规则收录原文引用、来源与核实日期，不只存一个
   布尔标志。没收录原文引用的规则，追踪会写明“未收录”，不编一条
   假原文顶上。
2. 来源证据：每件作品的每条事实（首次公开时间、已投比赛）带证据与
   来源，只收录台账里已有记录的事实，不编新数据。
3. 结论：由 MoonBit 当场算出。判定条件与 `detect_conflicts` 是同一套
   （标志位 + 台账字段），追踪只补上原文引用与事实证据，不另写一套
   判定；`evidence_test.mbt` 里“追踪与引擎 84 对全量一致”测试保证
   两者不脱节。有 P0 时，完整链后再输出一行“最短阻断链”——是哪 1–2 条
   规则直接导致不可提交（只收 P0，P1 不进链）；链与引擎 P0 数的一致性
   另有 84 对全量测试保证。平台上架目标走同一套三步链：规则 4（上架资质）
   与前三条规则的判定条件共用 `detect_conflicts`，追踪只补上
   规则原文引用与逐项证据，不另写一套判定；每项资质逐项比对
   目标的 materials 清单与作品的 materials_ready，缺口逐项列出。P0 冲突直接把投稿包标为 blocked，认证拒绝并逐项写清
   原因；无 P0、首次发布资格已核实、材料齐全且台账有效才算可提交。

P1 管的是“这件作品要改一改才能交”，材料缺口管的是“东西还没备齐”，

## 案例五：《第零次黎明》→ TapTap 游戏上架（非比赛目标，P1 资质缺口）

台账不再只管比赛：新增目标类型字段 `target_kind`，区分“比赛”与
“平台上架”。TapTap 与 itch.io 是两个真实的非比赛投稿目标——
作品投过去不是参赛，是上架发行；规则也不是“首次发布/须新做”，
而是上架前必须完成的资质清单。

规则适用条件：平台上架目标，要求完成 6 项上架资质
（target_kind = "平台上架"）。

规则原文：“每款游戏须完成四项资质：实名认证、AI 接入声明、
适龄分级、隐私合规；H5 游戏包内须含 index.html；大陆上架须
简体中文材料；人工审核”。

来源：TapTap 开发者上架要求（2026-11-16 核实：支持 H5 游戏；
四项资质、人工审核与简体中文材料要求来自官方上架流程）。

来源证据（逐项比对目标的 materials 清单与作品的 materials_ready）：

- 资质 1/6 实名认证——缺口。作品已就绪材料只有可体验原型链接、
  Qoder Sites 公开链接、作品链接，本项不在其中。
- 资质 2/6 AI 接入声明——缺口，同上。
- 资质 3/6 适龄分级——缺口，同上。
- 资质 4/6 隐私合规——缺口，同上。
- 资质 5/6 含 index.html 的 H5 游戏包——缺口，同上。
- 资质 6/6 触屏适配（移动端操作）——缺口。证据：2026-11-16 核实，
  《第零次黎明》目前是 PC 端 WASD+鼠标操作、无触屏适配。

推导：缺 6 项上架资质，未达到上架要求。

结论：P1——须补齐上架资质后才能上架。P1 不阻断投稿包认证：
本包最后仍是“不可提交”，原因只是材料缺口 6 项，与 P1 的
判定是同一份清单的两面——缺口本身已让认证拒绝，P1 只是把
“缺什么、为什么缺”逐项说清楚。

2026-11-18 实测输出：


## 诚实限定

- 魔搭规则原文来自 AIBetas 对官方页的转述，官网原文因登录墙未直接
  读到；追踪里写明了这一层，不把它当成官网原文。
- AI PLAY 提案已提交的证据是用户确认（2026-11-16），未独立核实；
  但本案例的 P0 结论不依赖它——只凭“11-02 前已公开”这一条，
  公开分支就足以触发。
- 造化“须用天工引擎新做体素游戏”的规则 2 只表达“须新做”，
  不表达引擎要求；两件工具作品对造化显示“无冲突”，不等于能交
  （它们不是游戏）。
- TapTap 四项资质与 H5 包要求 2026-11-16 核实自官方上架流程
  （开发者后台，登录后可见），无稳定公开链接可供复核；追踪里
  写明来源，未编造链接。
- itch.io 规则 2026-11-18 逐字核实自官方文档
  （https://itch.io/docs/creators/html5 与
  https://itch.io/docs/creators/quality-guidelines）；“HTML5 游戏
  仅接受捐赠”等页面细节未收进资质清单——清单只含上架前必须
  完成的 6 项。
- TapTap 触屏缺口的证据是 2026-11-16 的核实记录（PC 端 WASD+
  鼠标操作、无触屏适配）；若后续做了触屏适配，须人工更新作品
  的 materials_ready，追踪才会变通过——机制不自动探测游戏内容。
- itch.io 资质清单含“封面图与截图”：黎明的松江存档里已有封面与
  截图文件，但未登记进作品的 materials_ready，机制按“未就绪”计
  ——这是登记缺口，不是文件不存在；补登记即可。
- 平台目标无截止、无现金奖：prize 字段写的是上架方式说明
  （如“无奖金；上架发行”），不是奖金；撞期检测跳过无截止目标，
  两个平台目标不会互相撞期。
